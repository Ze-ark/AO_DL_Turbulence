## 1. 这次要回答什么

第一次 S3 训练中，GRU 输给了使用相同 8 帧历史的线性岭回归。现在只回答两个问题：

1. GRU 是不是因为独立训练回合太少才失败？
2. 当前隐藏维度 128 的 GRU 是不是太大了？

这是开发性诊断，不是重复原实验，也不会打开原来的封存测试。

## 2. 数据量学习曲线

保持 GRU 隐藏维度为 128，分别使用：

| 训练规模 | 每个物理条件的回合数 | 总完整回合数 |
|---|---:|---:|
| 很小 | 8 | 48 |
| 小 | 16 | 96 |
| 当前规模 | 32 | 192 |
| 加倍 | 64 | 384 |

六个物理条件始终均衡；每种物理条件的两批独立种子也等量取样。程序按完整回合选择数据，不随机拆散重叠时间窗口。

每个规模使用 3 个不同模型初始化种子，避免把一次初始化的运气当成结论。

## 3. 模型大小诊断

固定使用 192 个完整回合，比较：

```text
隐藏维度 32
隐藏维度 64
隐藏维度 128
```

每个大小同样运行 3 个初始化种子。如果较小模型的平均误差至少低 5%，说明原来的 128 维 GRU 可能参数过多。

## 4. 怎样保证公平

每个设置都固定为：

- 3600 次参数更新；
- 批大小 256；
- 相同优化器与学习率；
- 每 120 步检查一次相同的新验证集；
- 相同 8 帧输入和十模态目标；
- 同训练数据拟合的线性岭回归基线。

固定参数更新次数，是为了避免“数据多的模型同时训练得更久”这个混淆。

总共训练 18 个小模型：12 个用于数据量曲线，另外 6 个用于补齐小模型容量比较。

## 5. 预先规定的判断方法

支持“数据太少”必须同时满足：

1. 从 192 增加到 384 回合后，GRU 误差至少再降低 10%；
2. 从 48 增加到 384 回合后，GRU 相对线性岭回归的差距至少缩小 25%。

如果 192→384 回合改善不超过 5%，或者相对线性模型的差距完全没有缩小，则不支持“数据太少”解释。介于两者之间记为“证据不足”。

这些阈值已写入配置，不会在看到结果后修改。

## 6. 你在 IDE 中运行

在项目根目录的 IDE 集成终端执行：

```powershell
.\.venv\Scripts\python.exe scripts\train_s3_data_scaling_diagnostic.py --config configs\experiments\s3_data_scaling_diagnostic_v1.yaml
```

终端会实时显示：

- 384 回合训练池和新验证集的生成进度；
- 18 个模型的总体进度；
- 每个模型的 3600 个更新步骤；
- 训练误差、验证误差、最佳误差；
- 预计剩余时间和 CUDA 显存。

训练期间每个模型都会持续保存独立损失历史和最佳检查点。即使中途报错，已完成模型的 `run_records.csv` 仍会保留。

## 7. 完成后

主要输出：

```text
outputs/s3_data_scaling_diagnostic_v1/summary.json
outputs/s3_data_scaling_diagnostic_v1/run_records.csv
outputs/s3_data_scaling_diagnostic_v1/learning_curve.csv
outputs/s3_data_scaling_diagnostic_v1/capacity_curve.csv
outputs/s3_data_scaling_diagnostic_v1/loss_histories/
checkpoints/s3_data_scaling_v1/
```

终端出现下面提示后停止：

```text
请停止在这里并告诉助手“诊断训练完成”。
```

不要运行原 S3 封存评估。助手会读取学习曲线，判断是数据不足、模型过大，还是当前任务本身主要为线性动态。

## 8. 证据边界

这个诊断使用新的开发训练与验证种子。它只能帮助解释第一次 S3 失败，不能推翻原来的验证结果，也不能证明 RL 有效。原 S3 封存种子继续保持未打开。

## 9. 已完成结果与后续

本诊断已经完成：192→384回合仅改善4.53%，不支持“单纯数据不足”；32和64维均比128维更差，不支持“128维模型过大”。但是多数模型在3600步附近仍在改善，因此后续进入 [S3 收敛与 256 维容量复查](S3收敛与256维容量复查计划.md)，原封存测试继续关闭。
