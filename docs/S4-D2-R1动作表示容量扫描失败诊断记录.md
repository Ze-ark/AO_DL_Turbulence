## 结论先说

第一次正式扫描不是CUDA崩溃，也不是湍流轨迹不一致。522/522条任务均已完成，程序最后在真值对齐检查处停止。根因是256维动作下使用“残余模态减已施加模态”恢复湍流真值时发生float32单精度消差，最大误差为`2.3841857910e-6`，超过未放宽的`1e-6`门槛。

直接从仿真湍流相位投影模态时，同种子两个环境的误差为严格的`0`。因此修复选择更正真值读取方法，而不是放宽门槛。

## 根因证据

原方法从观测中计算：

```text
湍流模态 = 残余相位模态 - 已施加相位模态
```

这在数学上成立，但高维动作较大时两个float32数值接近，相减会损失有效数字。只读复现得到：

| 检查 | 最大误差 |
|---|---:|
| 观测相减法 | `1.9073486328e-6` |
| 正式故障场景0—6帧预见 | `2.3841857910e-6` |
| 直接湍流相位投影 | `0` |
| 固定门槛 | `1.0e-6` |

误差呈现float32量化步长的整数倍，并且直接真值严格一致，说明这是诊断读取方法的数值问题，不是动态湍流、SLM动作或随机种子发生分叉。

## 修复内容

1. `AdaptiveOpticsEnv`新增`oracle_disturbance_modal()`，直接把当前湍流相位投影到动作基；
2. 动作表示扫描的未来真值和当前真值统一使用该接口；
3. `truth_alignment.method`明确记录为`direct_turbulence_modal_projection`；
4. 保持真值对齐门槛`1e-6`不变；
5. 如果以后仍然失败，程序会先写`scenario_records.csv`和带有`TRUTH_ALIGNMENT_FAILED`状态的`summary.json`，再抛出包含最大误差的异常；
6. 新增256维回归测试，确保不同SLM动作不会改变同种子湍流真值。

该接口属于显式oracle（理想真值）诊断，不能作为可部署策略观测，也没有改变奖励、控制器、动作预算、硬件误差或评价门槛。
